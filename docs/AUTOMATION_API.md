# 自动识别、听牌草稿与半自动和牌

牌面识别为可选 Demo。试用时在源码目录使用兼容的 Python 3.11 或更高版本运行 `INSTALL-Automation.cmd`，安装组件并校验下载本机 ONNX 模型，再启动导播台。识别手牌显示在各选手行下方，听牌和和牌建议进入原有待牌、役种和计分控件。[识别依赖](../requirements-recognition.txt) · [模型来源](../resources/recognition/THIRD_PARTY.md)

## OBS 与摄像头

四机位由 OBS 采集。各来源使用独立的 Spout 发送名和持续发送设置，导播台分别绑定四个固定桌位。 [四机位接入步骤](OBS_MULTI_CAMERA_DESIGN.md)

**OBS Virtual Camera** 保留为兼容输入；它只有一条视频流，若承载四个镜头，必须把四路同时放在固定的专用场景并独立裁切，不能把跟随 Program 的单镜头画面当成四路。固定 Scene/Source 的行为见 [OBS 虚拟摄像头说明](https://obsproject.com/kb/virtual-camera-guide)。

支持按名称选择硬件摄像头、采集设备和已注册的虚拟摄像头。系统保存设备稳定标识；USB 设备排序变化后仍匹配同一设备。设备断开、被占用或 OBS 虚拟摄像头未启动会显示连接错误。设备列表中的注册项不代表当前一定有有效视频输入。已交给 OBS 的硬件优先通过独立 Spout 来源共享。

## 导播操作

1. 打开「赛事管理 → 赛事设置 → 画面与设备 → 牌面识别」，或从选手手牌行末尾的 `…` 进入来源设置。为固定位置选择 Spout、摄像头、视频或图片。
2. 选择要查看的席位，点 **连接预览**，即可查看视频及识别框。在画面上拖选仅包含该选手暗手牌的区域，百分比坐标和实时识别结果同步更新；可逐席查看各路画面和手牌结果。预览与裁选只影响识别范围，不修改 OBS 播出。
3. 点原设置窗口的 **保存**，启用该来源。未保存的预览不写入对局、也不提交建议。配置随赛事保存。ML 实图和构造听牌回放预设可用于无摄像头验收，构造回放有明确标注，并非实战比赛手牌。
4. 原选手列表下会显示各自识别的手牌及状态，自动按万、筒、索、字牌排序，赤五与普通五相邻。实时画面连续 3 个新帧一致且符合牌数与可信度后，自动计算听牌并辅助填入原待牌草稿，不切换导播当前选手或抢焦点。点一张识别牌可进入行内修正，用共用大牌区替换或补牌；可删除、采用或取消。编辑中位置暂不重排，采用后统一排序并重新计算。手动修正保持至本局结束或明确恢复自动识别，后台画面不会覆盖编辑。牌谱文字输入保留为可选方式。
5. 在原听牌区核对待牌、无役、振听和山存量，按原 **提交**；也可直接按该选手或快捷栏的 **听牌／立直** 确认。立直供托和待牌一次提交，可以一起撤销。人工改动会保留；新的自动结果不会覆盖正在修改的草稿。
6. 和牌时，在原 **役种** 区输入和牌张、里宝牌**指示牌**，通过原按钮选择立直、一发和荣和／自摸、和牌者及放铳者。系统直接辅助填写役种、宝牌数、番与符；13 张与已含和牌张的 14 张按实际暗手牌数量区分，副露自动从系统读取。
7. 和牌张和里指示牌都可通过共用大牌面区点选；原役种高亮按钮仍可手动调整。手动改过的役种、番符不会被后台更新覆盖；如需重新采用计算结果，点 **更新役种**。原位预览显示和牌者、放铳者、符番和四家收支，核对后按 **提交结算**；听牌区同样直接显示待提交与已播出内容，不增加确认弹窗。

直播来源超过约 4 秒没有稳定新识别、发生断流、跨局或换来源后，未确认的自动建议会过期；旧自动和牌结果不能继续结算或“更新和牌”。已提交的播出状态和人工草稿由导播控制。宝牌或规则改变会重算当前手牌并保留和牌输入；某家副露改变只要求该家重新识别暗手牌。

无役待牌按**荣和**判断，门前自摸可能另有役。振听需要牌河和临时振听信息，保留人工确认。已知可见牌导致的空听仍显示结构待牌，计算结果另有 `exhausted_waits`。宝牌不能单独成为役；未立直不计里宝牌。原明宝牌区选的是实际宝牌，内部转换成指示牌；役种区的里宝牌字段明确输入指示牌。

## 可替换的接口

未启用来源时，原导播台不显示空的手牌状态行。停止某个位置或在设置中取消启用并保存，会收起对应手牌及编辑入口，并撤下未提交的识别建议；已上播的待牌和立直状态不变。`UNINSTALL-Automation.cmd` 只卸载本项目环境中的可选视觉识别和 Spout 接收组件，保留赛事、模型、手动导播与计算功能。已打开的导播台也会检测本地识别组件缺失、停止读取并收起手牌；运行卸载脚本前仍应关闭导播台，避免 Windows 占用中的文件妨碍卸载。外部程序通过统一接口提供新结果时，对应选手仍可显示手牌。

原 `Model`、对局状态和结算引擎不依赖 YOLO。模块分工如下：

| 模块 | 作用 | 依赖方向 |
|---|---|---|
| `automation_api.py` | JSON v1 校验、草稿收件箱、本机 HTTP 接口 | 仅 Python 标准库 |
| `automation_bridge.py` | 将草稿接到原导播台；确认时调用原操作 | 知道 Model 和界面，识别模型不进入此层 |
| `hand_calculation.py` | 独立的听胡牌计算 | 普通数据输入输出、mahjong 库，无 Qt/Model |
| `tile_recognition.py` | 独立识别提供者 | 图像输入、牌面/可信度/坐标输出，无对局状态 |
| `spout_capture.py`、`shared_camera.py` | 来源接收与共享采集 | 不依赖对局、Qt 或特定识别模型 |
| `recognition_worker.py` | 后台读取图像/视频/摄像头并运行识别 | 可注入其他识别提供者 |
| `inline_automation.py` | 把建议辅助填入原导播控件、保留人工修改 | 消费统一接口，自动结果不发布 |
| `recognized_hand.py` | 原选手行下显示与修正手牌 | 纯界面，不依赖 Model/识别器 |
| `camera_devices.py`、`recognition_source_editor.py` | 设备选择、设置内预览与拖选区域 | 来源配置与诊断，不写入对局 |

外部程序可以只提交 `tiles`（牌面供计算）、`waits`（已算好的听牌建议）或 `win`（已算好的和牌建议）。可以完全替换内置识别和计算程序，无需修改原导播的手动操作、赛事数据或结算流程。

人工采用修正后，该固定位置暂停采用新的自动草稿，外部提交将转为 `dismissed`，直至导播选择“恢复自动识别”。宝牌变化仍会依据已经确认的人工手牌重新计算。

草稿暂存在内存中；收到草稿不改变比分、播出和撤销记录。换局、换赛事、修改副露/宝牌/场风等上下文或恢复历史后，旧草稿会失效。导播确认时再次检查上下文，已经处理的草稿不能重复提交。普通比分或资料更新也可能令旧建议失效，应重新获取上下文。

## 本机 HTTP v1

在「牌面识别」展开「识别参数与精确裁切」，点击「复制自动化接口连接」开启接口并复制地址与令牌。地址为 `http://127.0.0.1:随机端口`，认证头为 `Authorization: Bearer <令牌>`。接口随应用关闭，重新启动时生成新令牌。提交的外部建议进入导播台草稿。

| 方法与路径 | 结果 |
|---|---|
| `GET /v1/context` | 当前 `context_id`、对局与四席的计算所需数据、支持的役名 |
| `POST /v1/drafts` | 提交 JSON 草稿，返回 `201` 及草稿对象（`id`、`status: pending`） |
| `GET /v1/drafts` | 查询草稿及 `pending / stale / applied / dismissed` 状态 |

先读取上下文，再以同一个 `context_id` 提交。不要在生成旧画面结果后临时换成最新 ID；应在采集画面时记录上下文 ID，并在该 ID 下完成计算和提交。

三个类型共用请求头：

```json
{
  "schema_version": 1,
  "context_id": "先从 GET /v1/context 读取",
  "request_id": "摄像头编号-帧号或其他唯一标识",
  "source": "my-recognizer",
  "player": 0,
  "kind": "tiles",
  "data": {
    "tiles": ["1m", "2m", "3m", "1p", "2p", "3p", "1s", "2s", "3s", "1z", "1z", "1z", "2z"]
  }
}
```

`player` 是当前四席固定下标 `0..3`，以 context 的 `state.players` 为准，不能根据选手显示名称定位。`0m / 0p / 0s` 表示赤五；`1z..7z` 依次为东南西北白发中。手牌只提交暗手牌，不重复提交系统已有副露。

听牌请求的 `kind` 为 `waits`，`data` 为：

```json
{"waits":["2z"],"no_yaku":[],"furiten":false,"remaining":null}
```

`no_yaku` 必须是待牌子集。`remaining: null` 是未统计，`0` 是确认零张。最终是否立直、是否振听和无役由导播选择。也可以通过 `data.tiles` 附带暗手牌，供界面切换立直条件后重算无役状态。

和牌请求的 `kind` 为 `win`，`data` 例如：

```json
{
  "type":"ron","loser":1,"han":3,"fu":40,"yakuman":0,
  "yaku":["立直","一发"],"bonuses":{"dora":1,"aka":0,"ura":0}
}
```

`yaku` 使用 context 公布的中文役名，宝牌单列在 `bonuses`；`han` 包含宝牌。役满用 `yakuman` 表示倍数，`han` 为 0；界面所需 `fu` 用 30（役满结算忽略符数）。仅载入标准面板可表达的役种；番数与役种不一致会拒绝载入。`type` 为 `tsumo` 时 `loser` 不参与结算。

相同来源的同一 `request_id` 重复提交相同内容只返回同一份草稿；改变内容返回 `409`。上下文已变返回 `409`；无效字段返回 `400`；队列满返回 `429`。请求体上限 64 KiB，待确认草稿上限 100。

内置 Python 接口为 `console.automation.inbox.submit(payload)`，使用相同协议。外部示例客户端只依赖 Python 标准库：

```powershell
.\.venv\Scripts\python.exe scripts\automation_client.py --url http://127.0.0.1:端口 --token 复制的令牌 --player 0 --tiles 123m123p123s1112z
```

也可用 `--payload 草稿.json` 提交完整请求。示例客户端会先获取当前上下文；生产识别程序应在采集开始时保存上下文，按上述方式防止跨局误提交。

## 离线样例与验收

识别页可打开自己的图片和视频。准备好本机的构造听牌回放后，也可从「离线样例」载入，用于检查框选、稳定帧和草稿流程。默认优先使用 v2 Medium，未安装时会使用本机可用的 Small 或 Nano。[本地回放样例](../resources/recognition/samples/README.md) · [模型与素材来源](../resources/recognition/THIRD_PARTY.md)

遮挡、倾斜、分辨率及背景中的牌会影响检测。用实际摄像头验收时，应逐席检查牌面、裁框与光照。图片样本的检测统计可供复核，实际对局由导播确认。 [真实赛事小样本报告](../tests/fixtures/recognition/accuracy/README.md) · [开发检查](CHECKS.md)
